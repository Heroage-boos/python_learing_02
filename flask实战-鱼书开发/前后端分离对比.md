# 前后端分离 vs Jinja2 模板渲染 — Flask 开发模式对比

> 基于 fisher_end（Jinja2 单体）和 flask-cloudBook（前后端分离）两个项目的实际差异总结

---

## 一、架构总览

```
Jinja2 单体应用 (fisher_end)           前后端分离 (flask-cloudBook)
─────────────────────────────          ─────────────────────────────
         Browser                              Browser (Next.js)
            │                                      │
            │  HTTP GET /book/search                │  fetch /api/book/search
            ▼                                      ▼
    ┌──────────────┐                      ┌──────────────┐
    │  Flask App   │                      │  Flask App   │
    │  ┌─────────┐ │                      │  (REST API)  │
    │  │ Jinja2  │ │                      └──────────────┘
    │  │ 模板引擎  │ │                            │
    │  └─────────┘ │                      JSON {books, total}
    │       │       │                            │
    └───────┼───────┘                      ┌──────┴───────┐
            │                              │  Next.js App │
    完整 HTML 页面                          │  React 渲染   │
            │                              └──────────────┘
            ▼                                      │
        Browser                            渲染后的页面
                                                   │
                                                   ▼
                                               Browser
```

## 二、六大维度对比

| 维度 | fisher_end (Jinja2) | flask-cloudBook (前后端分离) |
|------|-------------------|----------------------|
| **路由返回** | `render_template('index.html')` | `json.dumps(obj, default=lambda o: o.__dict__)` |
| **参数获取** | `request.form` / `request.args` | `request.json` / `request.args` |
| **登录校验** | `@login_required` → 302 重定向 | `@auth_required` → JSON 401 |
| **页面跳转** | `redirect(url_for('...'))` | 前端 `window.location.href = '/'` |
| **静态资源** | `url_for('static', ...)` | 前端独立管理（Next.js public/） |
| **Cookie** | 后端设置/读取，浏览器自动携带 | 后端设置 + `credentials: 'include'` |
| **CORS** | 不需要（同源） | 需要配置跨域 |
| **路由前缀** | 无统一前缀 | `/api/` 前缀区分业务接口 |

## 三、路由与响应

### 3.1 Jinja2 模式

```python
# 服务端渲染 HTML 并返回
@web.route('/book/search')
def search():
    # 查询数据...
    books = BookCollection()
    books.fill(yushu_book, q)
    return render_template('search_result.html', books=books)
    # 返回完整 HTML 页面，{{ books.xxx }} 在模板中渲染
```

### 3.2 前后端分离模式

```python
# 后端：返回 JSON
@web.route('/api/book/search')
def search():
    q = request.args.get("q", "")
    books = BookSpider(q)
    books.keyword_search(q)
    book_collection = BookCollection()
    book_collection.collect_book(books, keyword=q)
    return json.dumps(obj=book_collection, default=lambda o: o.__dict__)
    # 返回纯 JSON，不包含任何 HTML

# 前端：接收 JSON 并渲染
const res = await api.books.list({ q: 'python' })
// res = { books: [...], total: 100, keyword: 'python' }
// 由 React 组件渲染为 HTML
```

### 3.3 json.dumps default 序列化

```python
# 问题：jsonify(book_collection) 报错
# TypeError: Object of type BookCollection is not JSON serializable

# 解决：使用 json.dumps 的 default 参数
return json.dumps(obj=book_collection, default=lambda o: o.__dict__)
# default 参数：遇到无法序列化的对象时，调用该函数
# o.__dict__ 将对象转为属性字典
```

## 四、参数获取

### 4.1 Jinja2 模式

```python
# HTML 表单提交
form = RegisterForm(request.form)
# request.form = ImmutableMultiDict([('email', 'test@qq.com'), ('password', '123')])

# URL 查询参数
q = request.args.get('q', '')

# 路径参数
@web.route('/book/<isbn>/detail')
def detail(isbn):
    # isbn 直接从 URL 路径中捕获
```

### 4.2 前后端分离模式

```python
# JSON body（fetch POST 请求）
form = RegisterForm(data=request.json)
# request.json = {"email": "test@qq.com", "password": "123", "nickname": "test"}

# URL 查询参数（GET 请求）
q = request.args.get('q', '')

# 路径参数（同 Jinja2 模式）
@web.route('/api/book/details/<isbn>')
def book_detail(isbn):
    # isbn 从 URL 路径中捕获
```

**关键差异**：
- Jinja2：表单数据在 `request.form` 中（`application/x-www-form-urlencoded`）
- 前后端分离：JSON 数据在 `request.json` 中（`application/json`）
- WTForms 适配：`RegisterForm(request.form)` → `RegisterForm(data=request.json)`

## 五、认证机制

### 5.1 Jinja2 模式：@login_required

```python
@web.route('/my/gifts')
@login_required
def my_gifts():
    return render_template('my_gifts.html')
```

**未登录时的流程**：
```
浏览器 GET /my/gifts
    │
    ▼
Flask @login_required 检测未登录
    │
    ▼
302 → /login?next=/my/gifts
    │
    ▼
浏览器跟随 302，跳转到登录页（显示登录表单）
    │
    ▼
用户登录成功 → redirect(next) → /my/gifts
```

**适用条件**：浏览器直接访问页面，302 重定向是自然行为。

### 5.2 前后端分离模式：@auth_required

```python
@web.route('/api/user/home')
@auth_required
def page_home():
    return success({"nickname": user.nickname, "email": user.email})
```

**未登录时的流程**：
```
前端 fetch /api/user/home (credentials: 'include')
    │
    ▼
Flask @auth_required 检测未登录
    │
    ▼
200 OK + Body: {"code": -401, "message": "请先登录", "data": null}
(HTTP Status: 401)
    │
    ▼
前端 request() 函数检测 res.status === 401
    │
    ▼
window.location.href = '/user/login'
    │
    ▼
React Router 渲染登录页面组件
```

**为什么不能用 302**：fetch/AJAX 收到 302 后不会让浏览器自动跳转，前端拿到的可能是登录页的 HTML。

### 5.3 自定义装饰器源码

```python
from functools import wraps
from flask import jsonify
from flask_login import current_user

def auth_required(fn):
    @wraps(fn)
    def wrapper(*args, **kwargs):
        if not current_user.is_authenticated:
            return jsonify({
                "code": -401,
                "message": "请先登录",
                "data": None,
            }), 401
        return fn(*args, **kwargs)
    return wrapper
```

### 5.4 前端拦截器

```typescript
// 统一的 fetch 封装
async function request<T>(url: string, options?: RequestInit): Promise<T> {
  const res = await fetch(url, {
    ...options,
    credentials: 'include'   // 跨域请求携带 cookie
  })

  if (res.status === 401) {
    window.location.href = '/user/login'
    throw new Error('未登录')
  }

  if (!res.ok) throw new Error(`HTTP ${res.status}`)
  return res.json()
}
```

## 六、页面跳转

| 场景 | Jinja2 模式 | 前后端分离模式 |
|------|-----------|--------------|
| 登录成功 | `redirect(url_for('web.index'))` | 前端 `window.location.href = '/'` |
| 注册成功 | `redirect(url_for('web.login'))` | 前端自动跳转或提示 |
| 登出 | `redirect(url_for('web.index'))` | 前端 `window.location.href = '/'` |
| 未登录访问 | 服务端 302 → `/login` | 前端 `window.location.href = '/user/login'` |

**核心差异**：Jinja2 模式中，跳转由后端通过 HTTP 状态码控制。前后端分离中，跳转由前端 JavaScript 控制。

## 七、CORS 与 URL 前缀

### 7.1 前后端分离需要 CORS

```python
# flask-cloudBook 可能需要的 CORS 配置
from flask_cors import CORS

app = Flask(__name__)
CORS(app, supports_credentials=True)
# supports_credentials=True 是必须的，否则浏览器会忽略 Set-Cookie
```

### 7.2 /api/ 前缀

两个项目对 API 路由的命名区别：

```python
# fisher_end（Jinja2 单体）
@web.route('/book/search')        # 无前缀，直接对浏览器
@web.route('/login')              # 无前缀

# flask-cloudBook（前后端分离）
@web.route('/api/book/search')    # /api 前缀，统一标识 API 接口
@web.route('/api/user/login')     # /api 前缀
@web.route('/user/cookie')        # 老式路由，无前缀（教学用途）
```

`/api/` 前缀的好处：
1. 前端可以给 `/api/*` 统一配置代理
2. 方便 Nginx 做路由转发
3. 语义清晰：区分页面路由和 API 路由

## 八、Cookie 与 Session

### 8.1 跨域 Cookie 传递

Jinja2 模式中，浏览器和后端同源（同一域名、端口），cookie 自动携带。

前后端分离中，前端（如 `localhost:3000`）和后端（如 `localhost:5000`）不同源，需要特殊处理：

```typescript
// 前端：credentials: 'include'
fetch('http://localhost:5000/api/user/home', {
  credentials: 'include'    // 告诉浏览器发送 cookie
})
```

```python
# 后端：配置 CORS 允许凭证
from flask_cors import CORS
CORS(app, supports_credentials=True)
```

### 8.2 后端设置 cookie

```python
# 登录时写入 cookie
login_user(user, remember=True)
# Flask-Login 内部调用 response.set_cookie('remember_token', ...)

# 登出时清空 cookie
logout_user()
# Flask-Login 内部调用 response.delete_cookie('remember_token')
```

## 九、静态资源管理

| 场景 | Jinja2 模式 | 前后端分离模式 |
|------|-----------|--------------|
| CSS/JS | Flask `static/` 目录，`url_for('static', ...)` | Next.js `public/` 目录，直接引用 |
| 用户上传图片 | Flask `static/uploads/` | 独立文件服务器或 OSS |
| 模板 | `app/templates/` | 无（前端组件代替） |
| 蓝图级静态 | `Blueprint(static_folder='...')` | 无此概念 |

## 十、选择建议

### 选用 Jinja2 模板渲染的场景

- 内容型网站（博客、文档站）—— SEO 友好，服务端直出 HTML
- 简单管理后台 —— 团队全栈但前端经验少
- 快速原型开发 —— 不需要前端工程化
- 对 JavaScript 依赖敏感的场景 —— 即使 JS 被禁用也能正常工作

### 选用前后端分离的场景

- 复杂交互的 Web 应用 —— 需要丰富的客户端状态管理
- 多端复用 API（Web + Mobile + 小程序）
- 团队前后端分工明确
- 需要 SPA 页面切换体验
- 需要离线能力（PWA）

### Fisher 项目的实际演进

Fisher 项目本身是一个教学项目，专门演示了从 Jinja2 单体到前后端分离的完整演进过程。它证明了**没有绝对的优劣**，两种模式各有所长，关键是根据团队和业务场景选择。
